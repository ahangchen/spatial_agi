# 经验教训与最佳实践

## 训练监控的重要性

**时间**: 2026-02-17
**经验**:

在长时间训练（如50 epoch，12+小时）中，智能监控系统至关重要：

**监控指标**:
- 训练损失和验证损失
- GPU使用率和温度
- 学习率变化
- Epoch完成进度

**监控机制**:
- Cron任务定期检查
- 状态文件记录上次报告
- 批次进度达到阈值时发送通知

**经验总结**:
- 15-20分钟检查一次，平衡及时性和资源消耗
- 只在epoch完成时发送完整报告，避免信息过载
- 自动检测异常（OOM错误、验证错误）

## 检查点保存策略

**时间**: 2026-02-17
**经验**:

在训练中遇到错误恢复时，检查点保存策略很重要：

**观察到的现象**:
- Epoch 11-14的检查点可能未保存或已覆盖
- 最新检查点总是覆盖旧检查点

**建议**:
- 保存多个epoch的检查点（如最近5个）
- 定期备份关键epoch（如25, 50）
- 检查点命名包含epoch编号

**教训**:
- 训练中断后能从多个checkpoint恢复
- 避免因覆盖导致进度丢失

## 远程桌面配置注意事项

**时间**: 2026-02-27
**经验**:

在Ubuntu 24.04配置远程桌面时，学到的经验：

**避免两个RDP服务同时运行**:
- gnome-remote-desktop和xrdp都会尝试绑定3389端口
- 会导致端口冲突，其中一个无法启动
- **建议**: 只保留一个，推荐xrdp（更稳定、兼容性好）

**用户权限配置**:
- xrdp需要读取TLS私钥（/etc/ssl/private/ssl-cert-snakeoil.key）
- 用户必须在`ssl-cert`组才能读取
- **命令**: `sudo usermod -aG ssl-cert $USER`
- **重要**: 添加组后必须注销重新登录才能生效

**会话管理**:
- 远程连接失败会留下"closing"状态的僵尸会话
- 僵尸会话堆积会影响新的远程连接
- **定期清理**: `loginctl list-sessions` 查看并清理

**诊断习惯**:
- 先看日志：`/var/log/xrdp/xrdp.log`
- 再看会话：`loginctl list-sessions`
- 检查权限：`groups` 和 `ls -la /etc/xrdp/*.pem`

**教训总结**:
1. 配置远程桌面时，先检查是否有其他RDP服务运行
2. 权限问题不会直接报错，需要主动检查用户组
3. 会话状态容易被忽视，但会影响连接稳定性
4. 完整的诊断流程能快速定位问题

## 研究质量优先原则

**时间**: 2026-03-03
**经验**:

在Spatial AGI每日研究任务中，关于是否使用GLM WebReader替代NotebookLM的经验：

**核心原则: 质量 > 速度**
- NotebookLM是首选，GLM仅用于失败情况
- 每篇论文15-20分钟是正常的
- 深度分析比快速完成更重要

**允许使用GLM的条件**:
- ✅ NotebookLM连接完全失败
- ✅ 多次重试后仍然超时（3次以上）
- ✅ 服务返回500/503错误
- ✅ PDF添加失败3次以上

**禁止使用GLM的情况**:
- ❌ 响应慢但能工作
- ❌ 为了加快速度
- ❌ 个人偏好
- ❌ 想早点结束

**违规后果**:
1. 视为任务失败
2. 需要重新执行NotebookLM流程
3. 记录到知识库作为教训

**教训总结**:
- 不要以"节省时间"为由偷懒
- 备选方案是应急措施，不是捷径
- 质量标准必须严格执行
- 记录实际执行时间和质量指标

## 文档完整性验证的重要性

**时间**: 2026-03-03
**经验**:

在UFO-4D论文文档提交中，发现文档不完整的问题：

**问题现象**:
- GitHub上文件只有518字节（应该是12KB）
- 缺少实验结果和性能指标
- 只有占位符内容

**根本原因**:
- 创建文档时未完成所有内容
- 提交前未验证文件大小
- 缺少完整性检查机制

**最佳实践**:
1. **提交前验证文件大小**
   ```bash
   # 检查文件大小（论文文档应>10KB）
   wc -c papers/*.md
   ```

2. **完整性检查清单**
   - [ ] 标题和摘要完整
   - [ ] 核心算法说明
   - [ ] 实验结果详细
   - [ ] 性能指标具体
   - [ ] NotebookLM问答记录
   - [ ] 个人思考和见解

3. **提交后验证**
   - 在GitHub上查看文件内容
   - 确认所有内容都已上传

**教训总结**:
- 文档大小是完整性的重要指标
- 提交前必须验证内容完整性
- 建立检查清单避免遗漏
- 提交后要二次确认

## Git仓库初始化的配置检查

**时间**: 2026-03-03
**经验**:

在spatial_agi仓库中，发现作者信息错误的问题：

**问题现象**:
- 所有提交显示为 "cwh <cwh@example.com>"
- 应该是 "ahangchen <cweihang@foxmail.com>"
- 影响所有6个历史提交

**根本原因**:
- 新仓库初始化后未配置用户信息
- 使用了全局默认配置
- 首次提交前未验证

**解决方案流程**:
1. 更新仓库Git配置
2. 使用filter-branch重写历史
3. 强制推送到远程

**预防措施**:
1. **新仓库初始化检查清单**
   ```bash
   # 1. 初始化仓库
   git init
   
   # 2. 立即配置用户信息
   git config user.name "ahangchen"
   git config user.email "cweihang@foxmail.com"
   
   # 3. 验证配置
   git config user.name
   git config user.email
   ```

2. **首次提交前验证**
   ```bash
   # 做一个测试提交
   git commit --allow-empty -m "Initial commit"
   
   # 检查作者信息
   git log --pretty=format:"%an <%ae>" -1
   
   # 如果错误，立即修正
   git commit --amend --author="ahangchen <cweihang@foxmail.com>"
   ```

3. **添加到项目文档**
   - 在AGENTS.md中记录Git配置要求
   - 在项目README中说明贡献者信息

**教训总结**:
- 新仓库初始化后立即配置用户信息
- 首次提交前必须验证作者信息
- filter-branch虽然能修正，但成本高（所有hash都会变）
- 预防胜于治疗
