# Reasmory: 3D Reconstruction as Explicit Memory for VLMs Spatial Reasoning

**arXiv**: https://arxiv.org/abs/2606.00963  
**Date**: 2026-05-31  
**Submitter**: Jixuan He  
**Affiliation**: Cornell Tech, Cornell University; NVIDIA; illoca AI; UC Merced

---

## Executive Summary

Reasmory (Reconstruction as Memory) is a test-time framework that enables Vision-Language Models (VLMs) to perform reliable spatial reasoning by constructing explicit 3D spatial memory and constraining their interaction with this memory through validated Domain-Specific Language (DSL) programs. The key insight is that simply exposing 3D reconstruction tools to VLMs is brittle—VLMs often invoke tools incorrectly, skip required transformations, or misuse intermediate results. In contrast, Reasmory formulates spatial reasoning as **structured program execution** over reconstructed memory, where programs are parsed and validated before execution.

**Core Finding:** Explicit 3D memory is most effective when accessed through **constrained, validated operations** rather than free-form tool calls. Reasmory consistently improves performance by 6–18% over strong baselines including GPT-5-mini and Gemini-3-flash on multi-view image and video spatial reasoning benchmarks.

## Q1: 核心算法原理

### 1.1 核心思想和动机

#### 问题陈述

Vision-Language Models (VLMs) 在空间推理任务上表现出不可靠性，特别是在以下任务中：
- **视角推理** (viewpoint reasoning): "如果我从这个角度移动到另一个角度，会看到什么？"
- **方向比较** (directional comparison): "两个物体之间的方向关系是什么？"
- **距离估计** (distance estimation): "两个物体之间的实际距离是多少？"

#### 根本原因

在多视图图像和单目视频中，相关的空间线索是**稀疏且分散**的，分布在冗余的观察中。这导致：
1. 添加更多帧反而增加视觉混乱，阻碍记忆而非改善理解
2. VLMs 需要更有效的方式组织和检索空间证据
3. **感知-回忆-推理管道具有内在的脆弱性**：感知或记忆中的失败会破坏空间表示，而空间转换中的错误会产生错误答案

#### 动机洞察

1. **Frame Selection 只能过滤现有观察**，无法构建几何一致的场景表示
2. **VLMs 与空间记忆的交互方式至关重要**：
   - 自由形式的工具调用是脆性的
   - GPT-5-mini 在 camera-transition 任务中仅使用 60% 的工具
   - 明确的工具使用规划可以将工具使用率提升到 83.2%，准确率额外提升 20 个百分点

### 1.2 主要技术方法

Reasmory 采用**三阶段架构**：

```
输入: 多视图图像/视频 + 空间推理问题
↓
阶段1: 3D 空间记忆构建 (Spatial Memory Construction)
↓
阶段2: 空间推理分解与 DSL 程序生成 (Question Decomposition & Planning)
↓
阶段3: 程序验证与执行 (Validation & Execution)
↓
输出: 空间推理答案
```

#### 组件 1: 显式 3D 记忆构建 (Explicit 3D Memory Construction)

**记忆表示：**

Reasmory 将场景表示为显式的 3D 空间记忆，形式为**彩色点云**（colored point cloud）。

给定多视图图像/视频帧 {V₁, V₂, ..., Vₙ}，使用前馈重建器 ℛ（如 Pi3 或 Depth Anything v3）估计：
- 密度深度图 {D₁, D₂, ..., Dₙ}
- 相机位姿 {T₁, T₂, ..., Tₙ}
- 相机内参 K

每个像素通过深度反投影到 3D：
```
x = Tᵢ⁻¹(Dᵢ(u,v) · K⁻¹[uv1])
```

其中：
- p = (u,v) 是图像像素坐标
- Dᵢ(u,v) 是深度值
- Tᵢ 是相机位姿变换矩阵
- K 是相机内参矩阵

每个 3D 点与其 RGB 值关联，形成场景的彩色点云表示。

**记忆组织：**

为了简化下游空间推理，记忆对齐到规范坐标系：
- 全局向上方向对齐到 y 轴
- 使用最小面积包围盒对齐将主导墙面方向与 x 轴和 z 轴对齐
- 这使得尺寸估计问题更容易处理

**语义增强：**

许多空间推理问题涉及类别或名称的物体，如椅子、桌子等。Reasmory 通过以下方式增强 3D 记忆：

**Algorithm 1: 基于多视图 3D 一致性的语义增强**

```
输入: 视图 {Vᵢ}ᵢ₌₁ⁿ, 重建的 3D 地图 {X⁽ⁱ⁾}ᵢ₌₁ⁿ, 查询类别 C
输出: 带类别标签、中心、关联 3D 点的 3D 物体实例 O

O ← ∅
for 每个类别 c ∈ C do
    # 在所有视图中提取类别特定的分割提案
    for 每个视图中类别 c 的提案 mask M do
        # 使用重建的 3D 几何将提案提升到 3D
        将 M 提升 3D: X³ᵈ = lift_to_3d(M, X⁽ⁱ⁾)
        存储被占据的 3D 网格单元
        # 与其他视图中的同一类别提案比较
        评分 M: cross_view_3d_agreement(M)
    end for
    # 保留足够一致的提案
    保留跨视图一致性高的提案
    # 构建连接一致提案的图
    构建类别特定的图
    # 贪婪合并连接的提案（每视图最多一个 mask）
    贪婪合并提案
    将每个合并的簇添加为 3D 物体实例到 O
end for
```

**关键技术：**
1. **SAM3 分割**：使用 SAM3 进行开放词汇分割
2. **几何引导的跨视图合并**：匹配占用网格单元，比传统 MaskClustering 更鲁棒
3. **稀疏视图设置**：匹配实际 VLM 推理管线的稀疏多视图观察设置
4. **在 ScanNet 上的表现**：在稀疏视图设置下，mAP50 从 16.7 提升到 38.4，mAP25 从 35.7 提升到 68.4

#### 组件 2: 空间推理分解 (Question Decomposition)

Reasmory 将每个空间推理问题映射为三个阶段：

**Algorithm 2: 空间推理分解**

```
输入: 问题 q
输出: 答案 a

# 阶段 1: 参考视角选择
V_ini ← SelectReference(q)          # 选择初始视角
V ← V_ini

# 阶段 2: 视角细化（循环直到准备好比较）
while ¬ReadyForComparison(V,q) do
    V ← RefineViewpoint(V,q)         # 通过旋转或平移细化视角
end while

# 阶段 3: 实体变换与比较
ℰ ← IdentifyEntities(q)             # 识别相关实体
a ← f(Tᵥ(ℰ))                         # 在视角 V 下比较实体
return a
```

**空间推理分解示例：**

| 问题 | 参考视角 | 细化 | 比较 | 算子序列 |
|------|---------|------|------|---------|
| "房间里有几张桌子？" | 无 | 无 | count(table) | Build → Query(table) → BEV(table) |
| "我从第一个视角移动到第二个视角，向哪个方向移动？" | camera1 | 无 | direction(ego, camera2) | Build → Query(cam1) → SetView(cam1) → Query(cam2) → BEV(cam2) |
| "如果我站在第 3 张图片的位置和朝向，背后是什么？" | camera3 | rotate(back) | visibility(ego, object) | Build → Query(cam3) → SetView(cam3) → Turn(back) → RGB |
| "如果我站在第 1 张图片的位置和朝向，向右转并向前走，会更接近粉色毛绒玩具和床头板吗？" | camera1 | rotate(right), move(forward) | direction(ego, plush toy) | Build → Query(cam1) → SetView(cam1) → Turn(right) → Step(forward) → RGB |

#### 组件 3: DSL 空间推理原语与程序规划 (Spatial Primitives & Program Planning)

**DSL 设计：**

Reasmory 设计了轻量级空间 DSL，这是一个受限制的 Python 子集，包含四类原子原语：

**表 2: 空间推理原语**

| 原语类型 | 操作 | 说明 |
|---------|------|------|
| **记忆构建** | build_static_memory, build_dynamic_memory | 构建/加载空间记忆（点云、相机轨迹、深度图） |
| **记忆查询** | query_camera_pose, query_3d_object_location | 查询相机位姿或 3D 物体位置 |
| **记忆变换** | set_viewpoint, step_camera, turn_camera | 更新当前视角（旋转、平移） |
| **渲染** | render_egocentric, render_semantic_bev, render_rgb_bev | 渲染自视角或鸟瞰图观察 |

**推理阶段约束：**

不同推理阶段允许的原语类型不同：

| 推理阶段 | 允许的原语类型 |
|---------|---------------|
| **参考视角选择** | 记忆构建、记忆查询 |
| **视角细化** | 记忆查询、记忆变换、渲染 |
| **实体比较** | 记忆查询、渲染 |

这种约束设计减少了无效推理轨迹，强制执行一致的执行状态转换。

**程序规划示例：**

```python
# 问题: "如何计算房间里的椅子数量？"
# 程序:
build_static_memory()          # 构建 3D 记忆
table_cam = query_camera_pose("camera1")  # 查询相机位姿
set_viewpoint(table_cam)       # 设置到相机视角
cameras = list_cameras()       # 获取所有相机
for cam in cameras:
    set_viewpoint(cam)         # 遍历所有相机
    objects = query_objects(category="chair")  # 查询所有椅子
    chairs.extend(objects)     # 收集椅子
count = len(chairs)            # 统计数量
```

#### 组件 4: 程序验证与执行 (Program Validation & Execution)

**AST 编译器验证规则：**

Reasmory 使用基于 AST 的编译器在执行前验证程序，检查六类规则：

**表 3: AST 验证规则**

| 类别 | 规则 | 说明 |
|------|------|------|
| **程序语法** | 受限 Python 子集 | 不允许装饰器、默认参数、可变参数、仅关键字参数、返回注解 |
| **工具使用** | 白名单原语 | 只能调用预定义的空间记忆原语 |
| **依赖一致性** | 定义前使用 | 变量必须在引用前定义 |
| **视角状态一致性** | 过期查询无效化 | 视角改变后，之前的查询结果无效，必须重新计算 |
| **执行纪律** | 无悬空运动 | 每个相机运动操作后必须至少有一个后续渲染调用 |
| **计划一致性** | 运动方向对齐 | 相机运动必须精确匹配分解中指定的方向 |

**编译器反馈机制：**

编译器发现无效程序后提供反馈，允许规划器通过少量重新生成尝试修复，大部分无效程序可以在几次尝试内修复。

**执行引擎：**

验证通过后，执行引擎在空间记忆上确定性地运行程序，产生：
- 查询结果
- 转换后的视角
- 渲染的观察结果

**最终推理器：**

Reasoner 使用执行输出（查询结果、渲染图像）和原始问题，产生最终答案。

### 1.3 算法流程和关键步骤

**完整的 Reasmory 管线：**

```
输入: 多视图图像/视频序列 {V₁, ..., Vₙ} + 空间推理问题 q
↓
步骤 1: 显式 3D 记忆构建
   ├─ 使用前馈重建器 ℛ 提取深度图、相机位姿、内参
   ├─ 反投影像素到 3D 点，形成彩色点云 X
   ├─ 对齐到规范坐标系
   └─ 语义增强: 使用 SAM3 提取类别提案，几何引导的跨视图合并
↓
步骤 2: 空间推理分解
   ├─ SelectReference(q): 选择参考视角
   ├─ RefineViewpoint(V,q): 细化视角（旋转/平移）
   └─ IdentifyEntities(q) + f(Tᵥ(ℰ)): 识别实体并比较
↓
步骤 3: DSL 程序规划
   └─ 使用空间原语生成程序 P
↓
步骤 4: AST 编译器验证
   ├─ 语法验证
   ├─ 工具使用验证
   ├─ 依赖一致性验证
   ├─ 视角状态一致性验证
   ├─ 执行纪律验证
   └─ 计划一致性验证
   └─ 无效程序 → 重新生成 → 返回步骤 3
↓
步骤 5: 程序执行
   ├─ 执行引擎运行程序 P
   ├─ 查询相机/物体信息
   ├─ 转换视角
   └─ 渲染观察结果
↓
步骤 6: 最终答案生成
   └─ Reasoner 使用执行输出 + 问题 → 最终答案
↓
输出: 空间推理答案
```

### 1.4 输入输出

**输入：**

1. **多视图图像或视频序列** {V₁, V₂, ..., Vₙ}
   - 每张图像分辨率：短边 378 像素
   - 视频重建：64 帧（稀疏推理：16 帧）

2. **空间推理问题** q
   - 问题类型：视角推理、方向比较、距离估计、可见性判断、数量统计等

3. **可选参数：**
   - 重建模型：Pi3（彩色点云）、Pi3X（度量深度）、Depth Anything v3
   - 分割模型：SAM3（开放词汇分割）
   - 动态场景：Flow3r（视频几何和相机位姿估计）

**输出：**

1. **空间推理答案** a
   - 问题的最终回答
   - 支持多种输出格式：文本答案、坐标、方向描述、数量等

**中间表示：**

1. **3D 空间记忆：**
   - 彩色点云 X
   - 相机轨迹 T
   - 深度图 D
   - 3D 物体实例 O（类别、中心、关联点）

2. **DSL 程序：**
   - AST 抽象语法树
   - 源代码
   - 验证状态（通过/失败）

3. **执行结果：**
   - 查询结果（相机位姿、物体位置）
   - 渲染图像（RGB、BEV、语义 BEV）
   - 视角状态

## Q2: 与 Spatial AGI 的关系

### 2.1 如何理解和表示空间

Reasmory 对空间的表示方式与传统 VLMs 有本质区别：

#### 传统 VLMs 的空间表示：隐式和分散

1. **Token 序列表示：**
   - 图像通过视觉编码器编码为视觉 token 序列
   - 文本问题编码为文本 token 序列
   - 空间关系隐式编码在 token 之间的注意力机制中
   - 问题：**信息分散、稀疏、难以组织**

2. **注意力机制依赖：**
   - 跨视图对应关系需要模型自己学习
   - 相机位姿、视角转换依赖视觉相似性推理
   - 问题：**缺乏几何一致性保证**

#### Reasmory 的空间表示：显式和结构化

1. **3D 几何表示：**
   - **彩色点云**：每个点带有 RGB 值和空间坐标
   - **几何一致性**：由重建模型保证
   - **结构化数据**：便于查询和操作

2. **语义增强的 3D 实例：**
   - 每个物体实例存储：类别标签、3D 中心、关联点集合
   - **开放词汇分割**：支持任意类别查询
   - **跨视图对齐**：几何引导的合并策略

3. **规范坐标系：**
   - 全局向上方向：y 轴
   - 主导墙面方向：x 轴和 z 轴
   - **便于尺寸估计和几何计算**

#### 空间表示的关键优势

| 方面 | 传统 VLMs | Reasmory |
|------|----------|----------|
| **表示形式** | 隐式 token 序列 | 显式 3D 点云 + 物体实例 |
| **几何一致性** | 无（依赖模型学习） | 有（重建模型保证） |
| **跨视图对应** | 注意力机制 | 几何约束 |
| **结构化程度** | 低（分散在 token 中） | 高（结构化数据结构） |
| **可查询性** | 差（需要搜索） | 好（直接查询） |
| **可操作性** | 弱（需要通过推理） | 强（程序化操作） |

### 2.2 如何处理空间关系

Reasmory 通过 DSL 程序化操作处理空间关系，而非依赖 LLM 的注意力机制。

#### 空间关系类型

1. **视角关系：**
   - **相机位姿查询**：`query_camera_pose(camera_id)`
   - **视角变换**：`set_viewpoint(camera_id)`、`turn_camera(angle)`、`step_camera(distance)`
   - **视角状态跟踪**：编译器确保视角状态一致性

2. **物体关系：**
   - **物体位置查询**：`query_3d_object_location(category, camera_id)`
   - **可见性判断**：`visibility(ego, object)`
   - **距离计算**：`distance(obj1, obj2)`
   - **方向判断**：`direction(ego, object)`

3. **视图关系：**
   - **渲染观察**：`render_egocentric(camera_id)`、`render_rgb_bev(camera_id)`、`render_semantic_bev(camera_id)`
   - **多视图比较**：程序化遍历和比较

4. **几何关系：**
   - **鸟瞰图渲染**：将 3D 地图投影到 2D BEV 视图
   - **语义分割渲染**：在 BEV 中显示类别
   - **尺寸估计**：基于点云的几何测量

#### 空间关系处理的关键机制

**机制 1: DSL 约束**

- **白名单原语**：只允许预定义的原语，防止误用
- **阶段约束**：不同推理阶段只能使用特定的原语
- **语法约束**：受限的 Python 子集，避免复杂语法

**机制 2: 编译器验证**

- **视角状态一致性**：编译器跟踪视角状态，过期查询自动失效
- **依赖一致性**：变量必须在引用前定义
- **执行纪律**：相机运动后必须渲染，避免悬空操作

**机制 3: 程序化执行**

- **确定性行为**：相同输入产生相同输出
- **可控性**：每个操作都有明确定义的效果
- **可调试性**：可以在执行前验证程序正确性

#### 空间关系处理示例

**示例 1: 计算两个物体的相对方向**

```python
# 问题: "从相机1到相机2的方向是什么？"
cam1 = query_camera_pose("camera1")
cam2 = query_camera_pose("camera2")

# 计算相机1到相机2的方向向量
direction_vec = cam2.position - cam1.position

# 将方向转换为方向描述
direction = direction_to_description(direction_vec)
print(f"从相机1移动到相机2的方向是: {direction}")
```

**示例 2: 判断物体是否在视角后**

```python
# 问题: "如果我站在相机3的位置和朝向后，身后有什么？"
cam3 = query_camera_pose("camera3")
objects = query_3d_object_location("chair", "cam3")

# 旋转视角到背面
turn_camera(cam3, 180)  # 向后转180度
ego_pos = cam3.position

# 检查哪些物体在视角后
behind_objects = []
for obj in objects:
    # 计算物体到相机的向量
    obj_vec = obj.position - ego_pos
    # 如果向量与相机朝向相反，则物体在背后
    if is_opposite(obj_vec, cam3.forward):
        behind_objects.append(obj.name)

print(f"背后有: {behind_objects}")
```

**示例 3: 路径规划**

```python
# 问题: "如果我站在相机1的位置和朝向，向右转并向前走，会更接近粉色毛绒玩具和床头板吗？"
cam1 = query_camera_pose("camera1")
objects = query_3d_object_location(["pink plush toy", "headboard"], "cam1")

# 旋转到右侧
turn_camera(cam1, 90)  # 向右转90度
step_camera(cam1, 1.5)  # 向前走1.5米

# 检查是否更接近目标物体
for obj in objects:
    old_dist = distance(cam1.position, obj.position)
    new_dist = distance(cam1.position, obj.position)
    closer = new_dist < old_dist

print(f"更接近粉色毛绒玩具: {closer}")
print(f"更接近床头板: {closer}")
```

### 2.3 对 Spatial AGI 的启发

Reasmory 为 Spatial AGI 的研究和发展提供了多个重要启发：

#### 启发 1: 记忆架构决定推理能力上限

**核心理念：** 没有好的空间记忆，再强的 LLM 推理能力也无法发挥。

**启示：**
- Spatial AGI 的核心不是更强的模型，而是更好的记忆架构
- **显式 3D 记忆** vs. **隐式 token 序列**：后者有本质区别
- 记忆必须支持：几何一致性、跨视图对应、语义锚定、可查询性、可操作性

**应用：**
- 设计专门的空间记忆数据结构
- 开发高效的空间记忆操作原语
- 建立**记忆-推理分离**的架构（perception-reasoning separation）

#### 启发 2: 约束化执行 > 自由工具调用

**核心发现：** 在空间推理领域，约束化的程序执行比无约束的工具调用更可靠。

**原因分析：**
1. **空间推理有内在几何约束：**
   - 视角变换的顺序和组合有约束
   - 坐标系转换需要严格遵循
   - 几何关系（如距离、方向）有数学定义

2. **LLM 的自由推理难以遵守约束：**
   - LLM 随机性大，容易忽略顺序约束
   - 难以维持复杂的中间状态
   - 容易产生幻觉或错误推理

3. **约束执行的优势：**
   - **确定性行为**：相同输入相同输出
   - **可验证性**：编译器可以在执行前验证正确性
   - **可调试性**：可以定位错误在程序中的位置

**启示：**
- Spatial AGI 应该设计**领域特定语言**（DSL），而非开放工具调用
- 编译器/验证器是必需组件，而非可选
- 程序结构应反映任务的自然分解

**应用：**
- 设计空间推理 DSL
- 实现编译器验证机制
- 开发调试和错误修复工具

#### 启发 3: 感知-推理分离的架构

**核心理念：** 感知（重建）和推理（程序执行）应该分离，各自优化。

**优势：**
1. **模块化设计：**
   - 感知模块专注于重建质量
   - 推理模块专注于程序规划和执行
   - 两者通过明确接口交互

2. **可优化性：**
   - 重建模型可以独立改进（如更快的 VFMs、更高的精度）
   - 推理模块可以独立优化（如更好的 DSL、更强的编译器）
   - 不需要端到端训练，降低复杂度

3. **可复用性：**
   - 同一空间记忆可以用于多个推理任务
   - 同一 DSL 可以复用到不同的重建器

**启示：**
- Spatial AGI 不应追求端到端训练
- 应该采用**感知-推理分离**的架构
- 通过接口解耦，提高可维护性

**应用：**
- 设计清晰的数据结构和 API
- 避免在 LLM 中直接操作重建结果
- 使用 DSL 作为显式接口

#### 启发 4: 几何先验的重要性

**核心理念：** 空间推理应该充分利用几何先验，而非从头学习。

**Reasmory 的做法：**
1. **3D 重建提供几何先验：**
   - 点云表示天然具有几何结构
   - 相机位姿提供尺度先验
   - 3D 对齐提供坐标系先验

2. **几何引导的语义增强：**
   - 使用 3D 网格单元对齐跨视图提案
   - 贪婪合并策略基于几何一致性
   - 避免纯视觉相似性的局限

**启示：**
- 空间推理不应该从零开始
- 应该充分利用几何先验
- 语义和几何应该紧密结合

**应用：**
- 设计几何感知的分割和跟踪算法
- 开发几何一致性的验证机制
- 利用 3D 先验指导推理过程

## Q3: 创新点和局限性

### 3.1 主要创新点

#### 创新点 1: 首次将 3D 重建作为显式空间记忆

**创新描述：**

Reasmory 提出了**显式 3D 空间记忆**的概念，将多视图图像或视频直接重建为 3D 记忆（彩色点云），而非：
- 隐式地编码在视觉 token 中
- 通过注意力机制推断空间关系
- 依赖端到端训练

**技术突破：**

1. **重建即记忆：**
   - 使用前馈 3D 重建模型（如 Pi3、Depth Anything v3）一次性重建整个场景
   - 点云同时编码：
     - **几何信息**：空间坐标、深度、相机位姿
     - **颜色信息**：RGB 值
     - **语义信息**：通过后续的语义增强提供
   - **几何一致性保证**：由重建模型保证，无需模型学习

2. **语义增强的 3D 实例：**
   - 基于 SAM3 的开放词汇分割
   - 几何引导的跨视图合并（跨视图 3D 一致性）
   - 原子 3D 对象实例化（类别、中心、关联点）

3. **对比其他工作：**
   - **MindJourney**：生成新视角，但缺少几何一致性
   - **Think3D**：使用 3D 重建工具，但无约束
   - **Spatial VLMs**：在训练中注入几何结构，推理时无显式记忆

**创新意义：**

- 建立了**感知（重建）-记忆（3D）-推理（DSL）**的清晰管线
- 为 Spatial AGI 提供了新的记忆架构范式
- 显式 3D 记忆可以用于多种推理任务，提高可复用性

#### 创新点 2: 轻量级空间 DSL 约束化执行

**创新描述：**

Reasmory 设计了**轻量级领域特定语言（DSL）**，约束 VLM 与空间记忆的交互，而非暴露自由工具。

**技术突破：**

1. **受限的原语接口：**
   - 白名单机制：只允许预定义的 11 个空间原语
   - 类型安全：每个原语有明确的输入输出类型
   - 阶段约束：不同推理阶段只能使用特定的原语组合

2. **AST 编译器验证：**
   - **语法验证**：受限 Python 子集，避免复杂语法
   - **工具使用验证**：确保只调用白名单原语
   - **依赖一致性验证**：变量必须在使用前定义
   - **视角状态一致性验证**：视角改变后过期查询自动失效
   - **执行纪律验证**：相机运动后必须渲染
   - **计划一致性验证**：相机运动方向必须匹配分解

3. **编译器反馈机制：**
   - 无效程序拒绝执行
   - 编译器提供反馈，允许规划器迭代修复
   - 大部分无效程序可以在几次尝试内修复

**对比其他工作：**

| 方法 | 工具使用 | 约束 | 验证 | 可靠性 |
|------|---------|------|------|--------|
| **ReAct** | 自由工具调用 | 无 | 无 | 低 |
| **Toolformer** | 自由工具调用 | 无 | 无 | 低 |
| **VISPROG** | 程序化组合 | 有 | 无（运行时验证） | 中 |
| **MSSR** | 3D 专家工具 | 有 | 无 | 中 |
| **Think3D** | 3D 重建工具 | 无 | 无 | 低 |
| **Reasmory** | DSL 原语 | 强约束 | 编译器验证 | 高 |

**创新意义：**

- **结构化优于无约束**：在空间推理领域，结构化的程序执行比自由形式的工具调用更可靠
- **编译器是必需的**：验证机制是保证可靠性的关键，而非可选
- **可调试性**：可以在执行前定位和修复错误

#### 创新点 3: 感知-推理分离的架构

**创新描述：**

Reasmory 明确采用**感知-推理分离**的架构，而非端到端的 VLM 训练。

**技术突破：**

1. **感知模块（重建）：**
   - 使用外部 VLMs（Pi3、Depth Anything v3）
   - 负责构建和更新 3D 空间记忆
   - 独立优化，无需考虑推理任务

2. **推理模块（DSL）：**
   - 使用通用 VLM（GPT-5-mini、Gemini-3-flash）
   - 负责问题分解、程序规划、答案生成
   - 独立优化，无需考虑重建细节

3. **接口设计：**
   - 显式 3D 记忆结构（点云、物体实例）
   - DSL 原语作为接口
   - 明确的输入输出格式

**对比端到端方法：**

| 方面 | 端到端 VLM 训练 | Reasmory 感知-推理分离 |
|------|---------------|----------------------|
| **优化目标** | 端到端损失 | 分别优化感知和推理 |
| **模块耦合** | 高度耦合 | 解耦，通过接口交互 |
| **可复用性** | 低（针对特定任务） | 高（通用架构） |
| **可优化性** | 困难（梯度很难传递） | 简单（模块独立） |
| **可调试性** | 困难（黑盒） | 容易（模块清晰） |
| **灵活性** | 低（固定训练任务） | 高（可应用于多种任务） |

**创新意义：**

- **简化系统设计**：无需端到端训练的大规模数据收集
- **提高可维护性**：模块独立，易于调试和改进
- **提高可扩展性**：可以独立升级感知或推理模块
- **理论清晰**：感知和推理职责明确，便于理论分析

#### 创新点 4: 几何引导的语义增强算法

**创新描述：**

Reasmory 提出了**几何引导的跨视图语义增强**方法，在稀疏多视图设置下显著提升 3D 语义分割性能。

**技术突破：**

1. **算法流程：**
   - 在所有视图中提取类别特定的分割提案
   - 使用重建的 3D 几何将提案提升到 3D
   - 将每个提案表示为被占据的 3D 网格单元
   - 计算跨视图一致性分数
   - 构建图并贪婪合并提案

2. **关键设计：**
   - **几何对齐**：使用 3D 网格单元对齐跨视图提案，而非纯视觉相似性
   - **稀疏视图鲁棒性**：在稀疏观察下仍然有效（对比 MaskClustering）
   - **开放词汇支持**：SAM3 支持任意类别查询

3. **性能提升：**
   - 在 ScanNet 上，稀疏视图 mAP50 从 16.7 提升到 38.4
   - 稀疏视图 mAP25 从 35.7 提升到 68.4
   - **对比 MaskClustering**：
     - 密集视图设置：相当（231 帧/场景）
     - 稀疏视图设置：显著提升（10 帧/场景）

**对比其他工作：**

| 方法 | 分割模型 | 跨视图合并策略 | 稀疏视图鲁棒性 | 开放词汇支持 |
|------|---------|---------------|---------------|-------------|
| **MaskClustering** | SAM2 | 视觉相似性 | 差 | 有 |
| **Reasmory** | SAM3 | **几何引导** | **好** | **有** |
| **Segment-Anything 3D** | SAM3 | 简单聚合 | 中 | 有 |

**创新意义：**

- 提供了在稀疏多视图设置下的可靠 3D 语义分割
- 几何引导比纯视觉相似性更鲁棒
- 为空间推理任务提供了高质量的 3D 语义表示

### 3.2 局限性

#### 局限性 1: 重建模型的精度依赖

**问题描述：**

Reasmory 的性能直接依赖于 3D 重建模型的精度和速度。

**具体表现：**

1. **重建精度影响推理：**
   - 错误的深度或相机位姿 → 错误的 3D 记忆 → 错误的推理
   - Reasmory 的实验使用 Pi3 和 Depth Anything v3，性能已经很高
   - 如果使用低精度重建器，性能会下降

2. **重建速度限制：**
   - 视频设置使用 64 帧重建，较慢
   - 稀疏推理使用 16 帧，但仍有一定延迟
   - 实时应用（如 AR、自动驾驶）可能无法接受延迟

3. **动态场景的挑战：**
   - 需要使用 Flow3r 等方法估计几何和相机位姿
   - 动态场景比静态场景更难重建
   - 重建误差会累积

**缓解措施：**

- 使用更快的重建模型（如 Gaussian Splatting）
- 减少帧数或使用自适应采样
- 在静态场景中使用预重建记忆

**未来改进方向：**

- 开发在线重建机制
- 改进动态场景的重建方法
- 提高重建精度和速度的平衡

#### 局限性 2: 单帧视角规划的限制

**问题描述：**

Reasmory 的 DSL 设计限制了一次只能查询和操作一个视角，不支持同时处理多个视角。

**具体表现：**

1. **无法并行操作：**
   - DSL 程序是顺序执行的
   - 无法同时查询多个相机或物体的状态
   - 需要循环遍历，增加程序长度

2. **复杂场景的性能瓶颈：**
   - 在多相机场景中，需要遍历所有相机
   - 在复杂场景中，需要查询多个物体
   - 程序长度增加，错误概率增加

3. **无法表达某些空间关系：**
   - 无法直接比较多个视角的观察结果
   - 需要额外的中间变量和逻辑

**示例问题：**

```python
# 问题: "哪些相机能看到椅子上的杯子？"（需要查询多个相机）
# Reasmory 的 DSL 程序需要:
cameras = list_cameras()
chairs = query_objects("chair")
for cam in cameras:
    for chair in chairs:
        if query_camera_pose(cam).visible(chair):
            results.append((cam, chair))
```

**缓解措施：**

- 简化场景或减少相机数量
- 使用多个程序片段
- 在 DSL 中添加批量操作（未来改进）

**未来改进方向：**

- 扩展 DSL，支持并行操作
- 引入批处理原语
- 优化循环效率

#### 局限性 3: 语义分割的局限性

**问题描述：**

Reasmory 的语义增强依赖于 SAM3 的分割质量，存在以下局限性：

**具体表现：**

1. **细粒度物体的分割困难：**
   - SAM3 在复杂背景下分割困难
   - 小物体（如杯子、瓶子）可能被忽略
   - 物体重叠时分割不准确

2. **开放词汇的性能不稳定：**
   - SAM3 在常见类别上表现良好
   - 在罕见类别上性能下降
   - 需要更多的示例或微调

3. **计算开销：**
   - 在 64 帧视频上使用 SAM3 处理所有帧
   - 增加了总体延迟
   - 对实时应用不够友好

**缓解措施：**

- 使用更强的分割模型（如 SAM-2）
- 减少分割帧数（只分割关键帧）
- 使用预训练的分割模型进行微调

**未来改进方向：**

- 开发更高效的分割方法
- 改进开放词汇分割性能
- 减少计算开销

#### 局限性 4: 静态场景假设

**问题描述：**

Reasmory 主要针对静态场景设计，对动态场景的支持有限。

**具体表现：**

1. **物体运动无法跟踪：**
   - 动态场景需要跟踪物体运动
   - Reasmory 的 3D 记忆是静态的
   - 物体运动会导致 3D 记忆过时

2. **相机运动和物体运动同时存在：**
   - VLM4D-Real 任务需要同时处理相机和物体运动
   - Reasmory 的主要优势在静态场景
   - 在动态场景中性能提升有限

3. **时间一致性挑战：**
   - 需要跨帧跟踪物体
   - Reasmory 不处理时间序列
   - 需要额外的跟踪机制

**实验证据：**

- 在 VLM4D-Real 上，性能提升较小（GPT-5-mini: +7.4%, Gemini-3-flash: +6.0%）
- 空间微调模型在动态场景上表现很差
- MindJourney 在动态场景中性能下降

**缓解措施：**

- 使用视频重建模型（如 Flow3r）
- 跨帧跟踪物体（使用光流或跟踪器）
- 更新 3D 记忆（增量更新）

**未来改进方向：**

- 开发动态场景的 3D 记忆更新机制
- 整合视频跟踪技术
- 设计时间感知的 DSL 原语

#### 局限性 5: 计算开销

**问题描述：**

Reasmory 的总体计算开销较大，可能不适合所有应用场景。

**具体表现：**

1. **重建开销：**
   - Pi3 重建 64 帧需要一定时间
   - SAM3 分割所有帧增加开销
   - 重建和分割是离线或预处理步骤

2. **程序规划开销：**
   - VLM 生成 DSL 程序需要时间
   - 编译器验证需要时间
   - 多次重新生成增加开销

3. **执行开销：**
   - 执行引擎遍历 3D 点云
   - 渲染图像需要计算
   - 查询操作需要空间索引

**计算开销分析：**

| 步骤 | 开销 | 主要瓶颈 |
|------|------|---------|
| 3D 重建 | 高 | Pi3 推理速度 |
| 语义增强 | 中 | SAM3 分割速度 |
| 程序规划 | 中 | VLM 推理 |
| 编译器验证 | 低 | AST 遍历 |
| 程序执行 | 中-高 | 点云查询、渲染 |

**缓解措施：**

- 缓存重建结果
- 预编译常用程序
- 使用更快的硬件
- 减少输入帧数

**未来改进方向：**

- 优化重建速度（如使用更快的重建器）
- 实现程序缓存
- 并行化执行
- 使用空间索引加速查询
